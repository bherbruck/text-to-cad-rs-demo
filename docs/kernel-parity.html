#Kernel parity: OCCT, solidcore and cadrs

text-to-cad runs on any of three geometry kernels behind the cad_kernel::Kernel trait:

  • occt: the default, Open CASCADE through occt-rs;
  • solidcore: tangency-labs solidcore at rev 6f5b831 (main of 2026-11-24; it was 4c938d2

    until then: see "solidcore rev bump" below). Build with cargo build -p cad --features solidcore, then start the server with cad server start --kernel solidcore;

  • cadrs: rvdende/cadrs's pure-Rust kernel (cadrs_kernel) at eb5899ef, as a git

    dependency. Build with cargo build -p cad --features cadrs, then start the server with cad server start --kernel cadrs. See crates/cad-kernel-cadrs/README.md.

This page records how closely they agree. It covers the conformance suite, the six examples, and the differences that are inherent to the kernels rather than bugs.

#Known differences

Fixed in the adapter while doing this comparison:

  • Spring (sweep along a helix). solidcore has no helix curve, so helix() is a C1 cubic

    spline through 32 points per turn. Sweeping along that spline was slow (16 to 30 s) and wrong: either "not a closed solid", or a volume of 99.8 where 712 was expected. The adapter now remembers that the wire is a helix. A planar face swept along it becomes solidcore's exact screw sweep, because a sweep along a helix is a screw motion. The volume now matches OCCT to 8e-7.

  • Loft twist. solidcore's skin pairs the curves of each section by parameter. A rounded

    square (9 curves) lofted to a circle (1 curve) twisted, giving a volume of 43247 against OCCT's 53241. The adapter now lines the sections up before skinning:

    • each section runs the same way as the first;
    • each starts nearest where the one before starts;
    • a full circle is cut into arcs at the angles of the other section's curves.

    The duct's loft is now 53205 against OCCT's 53241, a 0.07% difference.

    Straight-edged sections with different numbers of corners (a hexagon to a rectangle) still twisted: the kernel benchmark's feat-000/014/056-loft came out 6–25% below either untwisted pairing. The adapter now gives such sections the same corners first: each outline is split where any section has a corner, by angle round its own centre (curves::matched_corners; sections that are not star-shaped about their centre, or have a curved side, are left as they are). All three cases now match OCCT's volume to 1e-6.

  • Empty booleans. A common of bodies that do not meet, or a cut that removes everything,

    was an error on solidcore and cadrs ("the result is empty"), where OCCT returns an empty compound and the model goes on (16 cases of the kernel benchmark, plus 2 where OCCT failed elsewhere). Both adapters now return an empty body (an empty compound: no solids, volume 0) that later booleans take: a fuse or cut with it leaves the other side, a common with it is empty. cadrs has no empty compound, so its adapter marks one that holds no cadrs body. The conformance check empty_results covers it. All 18 cases now build on both kernels, within the Monte Carlo reference's error.

  • Section along a face. A plane lying exactly on a face (the DXF of a solid at z = 0) made

    solidcore's split leave one side empty, so the DXF failed. The adapter now takes the outline of the body's own faces on that plane.

  • Rounds in STEP. solidcore writes those rounds as CONICAL_SURFACE with a zero

    half-angle, which STEP does not allow. solidcore's own reader then refused the file ("cone with a negative radius or a semi angle outside (0, 90°)"); the wasm smoke test's openFile .step showed it. write_step now writes those faces as the CYLINDRICAL_SURFACE they are, which is exact because the parameterisation is the same. The conformance step_round_trip check now includes a filleted box.

  • Round faces. solidcore records a round along a straight edge as a cone with a zero

    half-angle. The adapter now reports these as Cylinder with their radius, so radius selectors work.

Inherent to the kernels (recorded, not fixed):

  • cadrs: duct shell. cadrs also refuses the duct's shell(">Z or <Z", -1.6) ("the boolean

    left an open shell"), with the rounded and the sharp join alike. With sharp corners (radius 0) both ends open (9437.8 mm³, against solidcore's 9433.3). cadrs's own loft of the duct is 53254.7, against OCCT's 53240.7 and solidcore's 53205.

  • cadrs: modelled threads. cadrs's boolean used to miss every intersection with a sweep

    along helix() ("the boolean left an open shell", or the operands handed back untouched: 2041.5 mm³ for examples/dogfood/10-printed-bolt.ts against 1990.2). The cause was the path, not the thread: the adapter swept along the helix wire's interpolating spline. It now sweeps along rational quadratic Béziers, 16 a turn, as cadrs's own Thread feature does (cadrs_core::rebuild::kernel_ops::thread), and cadrs cuts and trims those exactly. Modelled threads now build on cadrs, both the ridge construction (fuse and trim, the SDK's) and the groove construction (one cut, cadrs's own). The volumes agree with OCCT's and solidcore's to 0.01 mm³. The result check stays on every cadrs boolean (a common past its operands' common box, a cut past what it cut, a fuse that leaves meeting operands apart), so a miss is an error, never a wrong part. Times from crates/cad-kernel-conformance/tests/thread.rs (release, this box, 16 cores; wasm cold in node):

    buildocctsolidcorecadrscadrs, 1 threadcadrs wasm
    shank, ridge (fuse + trim)2.09 s35.4 s0.71 s2.28 s6.3 s

The SDK now cuts the groove: the bolt is 2006.31 mm³ on all three kernels (the full-depth groove; the ridge gave 1990.21). So cadrs modelled threads are correct, and natively faster than OCCT's. In the browser they are slower: 3.1 s for the bolt, against OCCT's 2.3 s native. cadrs's own web app is slow on threads for the same reasons: it runs the same route (this sweep and a cut), on one thread, in wasm. The 1-thread column runs with RAYON_NUM_THREADS=1. At solidcore 6f5b831 the solidcore column drops: ridge shank 35.4 → 14.6 s, groove shank 26.4 → 12.5 s, the groove bolt 33.1 → 11.9 s. The browser is slow for two reasons: wasm runs on one thread, against cadrs's rayon loops natively (3×), and a build at opt-level s is about 2.5× slower than native on one thread. build.sh now builds the cadrs flavour at opt-level 3: twice as fast (6.2 to 3.1 s) for 0.2 MB more gzip. Of the time on one thread, the cut is about half and the volume (mass properties over the swept faces) about a third.

  • Smooth edges. smooth_edges() (engine's new trait method) is implemented on solidcore and

    cadrs from their tessellations: an edge is smooth when its two faces' mesh normals (the surfaces' own) at the edge agree within 0.5°. The engine then leaves such edges out of broad fillet and chamfer selections, so tscad's wall-hook and cable-clip, which solidcore refused ("edge … has no blend (Smooth)"), now build on all three kernels at the same volume (9958.1 and 1015.8 mm³). The conformance check smooth_edges (an extruded rounded rectangle: 8 smooth edges, 16 sharp) passes on all three.

  • cadrs: three-section lofts. cadrs skins a loft through more than two sections its own way:

    it passes exactly through every section where OCCT and solidcore overshoot a little (0.01 mm), and on tscad's sketch-vase its outer loft is 0.3% above OCCT's (666385 against

    1. and its inner 0.7% below (585430 against 589738). OCCT and solidcore agree to 2e-4.

      Two-section lofts agree on all three to 1e-5. The vase's cut of one loft from the other is then wrong on cadrs (80955 mm³, reaching 2.4 mm past the outer loft); the adapter's result check now turns that into an error ("the cut reaches past what it cut").

  • solidcore rev bump (4c938d2 to 6f5b831, 867 commits). The adapter built against the

    new rev unchanged. Against the kernel benchmark's corpus (271 cases, one process each, run one at a time on this box, native release):

    • built 232 → 253 cases: the 18 empty booleans above (adapter), csg-109-d6-snap (solidcore

      no longer leaves it open), and the two scaling cases that timed out at 60 s (scale-plate-holes-500 now 17.8 s, scale-union-boxes-200 7.0 s);

    • nothing that built before fails now, and no volume moved past the reference's error;
    • 2.6× faster (geometric mean over the 232 cases both built), so solidcore now takes 6.3× OCCT's

      time instead of 16.5×. Booleans and mass properties gained most: tests/perf.rs bearing_608 8.1 → 1.41 s, gt2_pulley 6.2 → 1.16 s, gear_pair 4.2 → 1.72 s. The modelled M8x30 bolt is 33.1 → 11.9 s, and the thread's cut 13.2 → 1.0 s; its screw sweep (8.7 s) is now most of it.

    • one case got worse: feat-043-shell-csg was refused at once ("not supported yet: a vertex

      moved past the other end of an edge") and now runs past 60 s. It failed on OCCT's side of the comparison too (cadrs refuses it).

    • still failing: the duct shell (now "the body is not a closed solid facing out"), 5 shells of

      cut CSG (feat-002/009/021/050/075), 3 fillets or chamfers that cadrs or OCCT build (feat-005/011/041), csg-095-d5-snap (status 1001) and part-nema23 (cut, "not a closed solid"). Error texts changed with the rev (solidcore's errors now name their causes).

  • solidcore: speed. The parts library's gear pair took about 30 s on solidcore (release; about

    60 s through a debug server). Two fixes brought it to 4.3 s, 7×:

    • Spline segments are now the C2 cubic interpolation of their points (The NURBS Book's

      global interpolation). The C1 Catmull-Rom chains they used to be had triple knots that solidcore splits faces and edges at.

    • Line and circle edges are measured exactly from their ends, not integrated.

    The engine's edges() call, which had taken 17 s of the 30, now takes 0.9 s. The gear's volume also now matches OCCT to 0.1 mm³.

  • Drawings: hidden lines. cadrs uses its own hidden-line removal. solidcore draws its edges and

    the outlines of its curved faces from its tessellation, and splits them into seen and hidden runs with a 2048-pixel depth buffer. OCCT uses its own HLR.

  • cadrs: section is a sheet. section() on cadrs returns the cut faces lying on the plane

    as a sheet (kind Face/Shell), not a wire. Its edges are the section curves, which is all the DXF export and the conformance check read.

  • cadrs: planar faces. These are made by extruding the profile and keeping its cap, through

    cadrs's testkit internals (native::kernel::subset).

  • Duct shell (spring.ts). solidcore refuses shell(">Z or <Z", -1.6) on the

    rounded-square-to-circle loft. Opening the rounded-square end fails ("the result is not a closed solid", or "a gap in its offset's loops cannot be bridged"). With sharp corners (radius 0) both ends open fine, and opening only the circular top works (11368.9 mm³). The other way round, OCCT fails shell(">Z") alone ("Geom_TrimmedCurve::parameters out of range") but builds the two-ended shell. The two kernels' offsets fail on different inputs.

  • Face splitting. The kernels split periodic and swept faces differently:
    • gear: 112 faces against 109, because solidcore splits the bore and its chamfers into more faces;
    • knob: 59 against 58;
    • spring: OCCT splits the swept tube into 12 faces, solidcore's screw sweep gives 3 (wall and

      two caps).

    Volumes and bounds still agree. Selectors that count faces can see different numbers.

  • Helix wire. On solidcore and cadrs, helix() is a spline approximation, within about 1e-5 of the radius. Its

    length is within 1e-3 of the true helix. Only a sweep along it is exact: solidcore's screw sweep, and on cadrs the sweep runs along rational Béziers (exact arcs in plan, within about 1e-3 of the pitch) with SweepControl::Helix. All three kernels start the helix on world X made square to the axis (world Y for an axis near X), and the conformance suite now checks this.

  • Spline segments. On solidcore and cadrs, Segment::Spline is a Catmull-Rom cubic through the points. It passes

    through every point and is C1, but it is not OCCT's interpolating B-spline, so the curves differ between the points.

  • Knob volume, 1.3e-5 relative. The knob's revolved torus band is cut by 24 cylinders.

    OCCT's result differs from solidcore's and cadrs's by 0.13 mm³, while those two agree with each other to 1e-9. The snapshots match.

  • Spring STEP read by OCCT: 707.2 against 712.05. solidcore writes the screw-swept wall as

    its NURBS form. OCCT's volume of that NURBS differs by 0.7%. solidcore reads its own file back at 712.05.

  • Mesh density. solidcore-tess honours the facet angle (28.5° by default for export), so

    thin tubes get few facets: the spring's 1.2 mm wire has about 13 sides, a −2.8% volume error. OCCT's mesher refines the same spring to about 680k triangles against solidcore's 16k. Pass --angle to cad model export for finer solidcore meshes.

  • Speed. Every solidcore call runs on one process-wide kernel behind a lock. Builds are

    about 5 to 10 times slower than OCCT in this debug build (gear 3.6 s against 0.33 s, knob 4.3 s against 0.46 s, spring 25 s against 8 s).

  • Index order. Face and edge indices follow solidcore's record order, not OCCT's TopExp

    order. Selectors work by geometry, so this matters only to raw indices.

  • Wires and compounds. These are held by the adapter, not by solidcore. to_native of a

    wire is Unsupported.

  • STEP import. Assembly placements are applied. Colours are not read.

#Running each kernel

One binary can carry all three kernels, each behind a cargo feature. Each server keeps its own documents under its CAD_HOME:

cargo build -p cad --features solidcore,cadrs
cp .occt/lib/libocct_capi.so target/debug/          # OCCT's module, next to the binary

CAD_HOME=~/.cad-occt      cad server start --port 7979 --kernel occt
CAD_HOME=~/.cad-solidcore cad server start --port 7980 --kernel solidcore
CAD_HOME=~/.cad-cadrs     cad server start --port 7982 --kernel cadrs

CAD_HOME=~/.cad-cadrs CAD_PORT=7982 cad run examples/gear.ts   # runs on that server
CAD_HOME=~/.cad-cadrs CAD_PORT=7982 cad server stop

cad --version names the kernels a build has. A kernel that was built without its feature is refused with that list. The comparisons on this page used ports 7979 (OCCT), 7980 (solidcore) and 7982 (cadrs), with a CAD_HOME for each in a scratch directory. Those servers have since been stopped.

#Browser (wasm)

crates/cad-wasm builds one module per kernel (FLAVOURS=occt|solidcore|cadrs crates/cad-wasm/build.sh). The files go to apps/viewer/public/wasm/.

Every flavour passes node crates/cad-wasm/smoke.mjs. The bracket's volume equals the analytic value (4477.805). Mesh, every export (step, stl, glb, 3mf, obj, brep), reopening its own STEP and STL exports, interference and the snapshot all pass. On cadrs the hinge mechanism ranges too.

On wasm32, cadrs needs one change: uuid's js source of randomness, which cad-kernel-cadrs turns on for wasm32 targets only. Nothing else needed gating, and rayon caused no trouble at runtime.

On solidcore, openFile .step on its own export failed before the STEP fix above (fillet rounds written as zero-angle cones). The wasm rebuild after the fix passes.
